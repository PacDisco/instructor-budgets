# Building the Android app

The instructor app is a PWA wrapped as a Trusted Web Activity — the same
approach as the instructor portal APK. The APK is a thin shell; all the code
lives on the Netlify site, so shipping a change means deploying the site, not
rebuilding the app.

## Option A — build in GitHub Actions (no local tooling)

One-time setup, then every APK is two clicks.

**1. Create the signing key locally.** This is the one step that has to happen on
your machine — the key is yours and should never be generated by CI or pasted
into a chat.

```bash
keytool -genkeypair -v -keystore android.keystore -alias fieldbudget \
  -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 android.keystore > keystore.b64      # macOS: base64 -i android.keystore -o keystore.b64
```

Back up `android.keystore`. It is the only key that can ship an update to an
installed app.

**2. Add three repository secrets** under Settings → Secrets and variables →
Actions:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_B64` | contents of `keystore.b64` |
| `KEYSTORE_PASSWORD` | the store password you chose |
| `KEY_PASSWORD` | the key password you chose |

Delete `keystore.b64` afterwards.

**3. Run it.** Actions → Build APK → Run workflow. Enter your hostname, a
version name, and a version code. Two minutes later the APK is at the bottom of
the run page under Artifacts.

The run also prints the SHA-256 for `assetlinks.json` — paste it into
`public/.well-known/assetlinks.json` and redeploy before installing.

Bump the version code (an integer that must increase) on every subsequent build.

## Option B — build locally

### 1. Prerequisites

Node 18+ and a JDK. Bubblewrap offers to download the Android SDK and JDK on
first run if it can't find them.

```bash
npm install -g @bubblewrap/cli
```

## 2. Configure

```bash
cp twa-manifest.example.json twa-manifest.json
```

Replace every `budget.pacificdiscovery.org` with your real hostname. Check
`packageId` — it must differ from the instructor portal's, or installing this
will replace that app on the fleet.

## 3. Build

```bash
bubblewrap build
```

First run generates `android.keystore` and asks for a password. **Keep both.**
Lose the keystore and you cannot ship an update to an already-installed app —
every device has to uninstall and reinstall.

Output is `app-release-signed.apk`.

## 4. Digital Asset Links

Without this the app runs with a browser URL bar across the top.

```bash
bubblewrap fingerprint list
```

Copy the SHA-256 into `public/.well-known/assetlinks.json`, replacing
`REPLACE_WITH_YOUR_SIGNING_CERT_SHA256`. Deploy the site, then confirm:

```
https://<your-host>/.well-known/assetlinks.json
```

It must return JSON with `content-type: application/json`. Netlify serves
`.well-known` correctly from `public/` with no extra config.

## 5. Test on one device before the fleet

Install the APK and check:

- No URL bar. If there is one, asset links aren't resolving — the fingerprint,
  the package name, or the deployed file is wrong.
- Google sign-in completes and lands on the budget.
- The camera opens directly from the receipt button.
- Airplane mode: the app still opens, a spend still saves, and the header chip
  shows the unsynced count.
- Back out and reopen — the queued entry is still there.

That last pair is the one that matters. Everything else is cosmetic by
comparison.

## 6. Push through AirDroid Business

Upload the APK under app distribution, assign it to the instructor device
group, and push. Same flow as the instructor portal APK.

If the devices are in kiosk mode, add the new app to the allowed list or it
installs but can't be launched.

## Updating

Web changes need no new APK — deploy the site and bump `SHELL` in
`public/sw.js` so the service worker drops its cache.

A new APK is only needed when the icon, name, package, or TWA settings change.
Then bump `appVersionCode` (an integer, must increase) and `appVersionName` in
`twa-manifest.json`, rebuild with the same keystore, and push again.
